# F2.6-B — Mercado Pago Checkout Pro

**Estado:** Pendiente de credenciales del cliente · **Bloqueante para producción ecommerce**
**Depende de:** F2.6-A (Checkout Foundation, completado)
**No afecta a:** sorteos (siguen el flujo Yape manual independiente)

---

## Objetivo

Reemplazar el `NotConfiguredPaymentProvider` por una implementación real de **Mercado Pago Checkout Pro** + recibir confirmaciones de pago vía webhook seguro. El flujo cliente → carrito → checkout ya quedó listo en F2.6-A; solo falta la pasarela y el webhook.

## Pre-requisitos (acción del cliente)

Antes de empezar la implementación necesitamos:

1. **Cuenta Mercado Pago Perú** (negocio).
2. **Aplicación Checkout Pro** creada en el panel de desarrolladores.
3. **Credenciales sandbox** (`TEST-...`) — para desarrollo y staging.
4. **Credenciales producción** (`APP_USR-...`) — solo al pasar a live.
5. **Webhook secret** — usado para validar firmas HMAC (`X-Signature` header).
6. **URL pública del API** para el webhook (`https://api.purpura.club/webhooks/mercadopago`).

Variables a colocar en `.env` / Supabase Vault:

```
MERCADOPAGO_MODE=sandbox|production
MERCADOPAGO_ACCESS_TOKEN=<TEST-... o APP_USR-...>
MERCADOPAGO_PUBLIC_KEY=<para frontend futuro si se usa Brick — Checkout Pro no lo necesita>
MERCADOPAGO_WEBHOOK_SECRET=<secreto generado en el panel>
MERCADOPAGO_REFERENCE_SECRET=<secreto interno para firmar external_reference>
STOREFRONT_PUBLIC_URL=https://www.purpura.club
API_PUBLIC_URL=https://api.purpura.club
```

## Alcance de F2.6-B

### Backend

1. **`MercadoPagoModule`** que provee:
   - `MercadoPagoService` con `createPreference(input)`, `getPayment(id)`, `signExternalReference(orderId)`, `verifyExternalReference(token)`.
   - `MercadoPagoCheckoutProProvider` que implementa `PaymentProvider` (reemplaza `NotConfiguredPaymentProvider` vía DI swap).
2. **`WebhooksModule`** con:
   - `POST /webhooks/mercadopago` (público, sin JWT).
   - `WebhookSignatureGuard` que valida HMAC-SHA256 + timestamp anti-replay (5 min).
   - `RawBodyMiddleware` registrado solo para `/webhooks/*` en `main.ts`.
3. **Schema Prisma**:
   - Nuevo modelo `WebhookEvent` con `UNIQUE(provider, eventId)` para idempotencia.
   - Enriquecer `OrderPayment` con `providerName`, `providerPreferenceId`, `providerPaymentId` (UNIQUE), `providerStatus`, `providerRawSnapshot` (Json).
   - Nuevo modelo `CheckoutSessionIdempotency` opcional para `Idempotency-Key` del cliente (TTL 5 min).
4. **Tests**:
   - `MercadoPagoService` con fetch mockeado.
   - `webhook-signature.guard.spec.ts` (firma válida, inválida, timestamp viejo).
   - `mercadopago-webhook.controller.spec.ts` (idempotencia + delegación a `OrdersService.updateStatus`).

### Storefront

No requiere cambios significativos — la página `/checkout` ya delega en `verdict` del backend:
- `REDIRECT` → `window.location.assign(redirectUrl)` (ya implementado).
- `PENDING_SETUP` / `UNSUPPORTED` → pantallas existentes.

Opcionalmente, agregar polling ligero en `/checkout/success` para refrescar el estado mientras el webhook actualiza la orden:

```ts
useQuery({
  queryKey: ["account", "orders", orderNumber],
  refetchInterval: (q) => (q.state.data?.status === "PAID" ? false : 3000),
  // máximo 90 segundos, luego mostrar "estamos verificando tu pago"
});
```

## Diseño del flujo

### Crear preferencia (cliente → API → MP)

```
POST /checkout/sessions
  ↓
CheckoutService.createSession
  ↓ (F2.6-A: Order PENDING creada)
  ↓
MercadoPagoCheckoutProProvider.createCheckoutSession
  ├── external_reference = signExternalReference(orderId)
  │     = base64url(orderId + ":" + HMAC-SHA256(orderId, MERCADOPAGO_REFERENCE_SECRET))
  ├── back_urls.success = {STOREFRONT}/checkout/success?order={orderNumber}
  ├── back_urls.pending = {STOREFRONT}/checkout/pending?order={orderNumber}
  ├── back_urls.failure = {STOREFRONT}/checkout/failure?order={orderNumber}
  ├── auto_return = "approved"
  ├── notification_url = {API}/webhooks/mercadopago
  ├── items = [{title, quantity, unit_price, currency_id="PEN"}]
  ├── payer = {email, name, surname, identification}
  └── statement_descriptor = "PURPURA CLUB"
  ↓
MercadoPago Preference API
  ↓
OrderPayment.create(providerPreferenceId, status="PENDING")
  ↓
return { verdict: "REDIRECT", redirectUrl: preference.init_point }
```

### Webhook (MP → API)

```
POST /webhooks/mercadopago
  Headers: x-signature: "ts=<unix>,v1=<hmac>", x-request-id
  Raw body: { topic: "payment", action: "payment.updated", data: { id } }
  ↓
RawBodyMiddleware preserva Buffer original
  ↓
WebhookSignatureGuard
  1. Parse x-signature → { ts, v1 }
  2. Reject si |now - ts| > 300s (replay protection)
  3. computed = HMAC-SHA256(
       secret  = MERCADOPAGO_WEBHOOK_SECRET,
       payload = `id:${data.id};request-id:${requestId};ts:${ts};`
     )
  4. timingSafeEqual(computed, v1) → 401 si mismatch
  ↓
WebhookEvent.create({ provider, eventId, signatureValid: true, rawPayload })
  - UNIQUE(provider, eventId): si ya existe, return 200 OK no-op
  ↓
MercadoPagoService.getPayment(data.id)
  - GET https://api.mercadopago.com/v1/payments/{id}
  - Authorization: Bearer MERCADOPAGO_ACCESS_TOKEN
  - Re-verificación INDEPENDIENTE del body recibido
  ↓
verifyExternalReference(payment.external_reference) → orderId
  - Si HMAC no matchea → log + return 200 (firma inválida)
  ↓
switch payment.status:
  "approved"  → CheckoutService.markPaid(orderId, payment)
                 ├── prisma.$transaction:
                 │     ├── OrderPayment.upsert(providerPaymentId UNIQUE)
                 │     └── OrdersService.updateStatus(orderId, PAID)
                 │           ↳ state machine F2.4 valida PENDING→PAID
                 │           ↳ side effects: stock, membership, raffle, referral
                 └── return 200
  "pending"   → log + WebhookEvent.processedAt = now + return 200
  "rejected"  → log + return 200 (orden permanece PENDING)
  "cancelled" → log + return 200
```

## Reglas duras (heredadas de F2.6-A)

1. **NUNCA confiar en el body del webhook.** Siempre re-fetch contra `/v1/payments/{id}`.
2. **NUNCA marcar PAID desde el frontend.** `success_url` solo informa al usuario.
3. **NUNCA llamar a `OrdersService.updateStatus` desde el provider.** Esa responsabilidad pertenece al webhook handler.
4. **HMAC + timestamp** son obligatorios en todo webhook entrante.
5. **`external_reference` firmada** para prevenir tampering del orderId.
6. **Idempotencia doble**: `WebhookEvent.UNIQUE(provider, eventId)` + `OrderPayment.providerPaymentId UNIQUE`.

## Casos de error y cómo se manejan

| Escenario | Acción |
|---|---|
| Cliente cierra el navegador después de redirect a MP | Order queda `PENDING`. Webhook eventualmente la mueve a `PAID` o se queda `PENDING`. Cliente la ve en Mis Pedidos. |
| Pago rechazado | Webhook recibe `status=rejected`. Order permanece `PENDING`. Cliente puede reintentar desde Mis Pedidos (no en este alcance — agregar CTA "Reintentar pago" en F2.6-C). |
| MP retransmite webhook (red flaky) | `WebhookEvent` UNIQUE → return 200 no-op. |
| Atacante envía webhook falso a nuestro endpoint | HMAC mismatch → 401. Aunque pasara, `external_reference` firmada protege contra mover otra Order. |
| MP API caída al crear preferencia | `MercadoPagoService.createPreference` throw → `CheckoutController` retorna 502 al cliente. La Order PENDING queda registrada (admin puede crear preferencia manualmente o cancelarla). |
| `OrdersService.updateStatus` falla en webhook | `WebhookEvent.processedAt` queda `null`. Reintento manual posible vía script. |

## Diferencia explícita con sorteos

**Los sorteos NO usan Mercado Pago.** Mantienen su propio flujo:
- Cliente compra ticket vía Yape (transferencia manual).
- Sube comprobante en `RaffleEntriesService.purchase`.
- Admin valida manualmente y aprueba.
- Tickets se asignan al cliente.

Esa lógica vive en `apps/api/src/modules/raffle-entries/` y permanece intacta. El `PaymentProvider` de F2.6-A/B es exclusivo del módulo `Checkout` para ecommerce.
